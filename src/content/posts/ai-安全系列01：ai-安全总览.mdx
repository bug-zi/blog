# 第 01 讲：AI 安全总览

## 近三年 AI 安全发展总览：从模型风险到生态风险

---

### 1. 近两三年，AI 安全为什么突然变重要

我们可以不从技术史讲起，直接从自己的使用体验讲起：这两三年，我们和 AI 的关系，正在从"向它提问"变成"让它参与工作"，再变成"让它替我们行动"。

真正的变化，不只是 AI 变强了，而是 **AI 在真实系统中的渗透程度越来越深、使用规模越来越大、参与流程越来越长**。

**先看渗透程度**。AI 的使用大致经历了三个层次：

**第一阶段：对话参考。** AI 像一个随时可问的助教、搜索增强器或写作助手。用户问问题，AI 给建议，最后由人判断和执行。在这个阶段，主要风险是幻觉、误导和隐私泄露。它会影响人的判断，但行动权还在人手里，所以破坏半径相对有限。

**第二阶段：协同执行。** 这时的 AI 不再只是聊天窗口，而是嵌入到具体工具和插件里：IDE 里的代码补全插件、代码审查插件，数据分析平台里的 SQL 生成与图表生成能力，企业知识库里的 RAG 问答模块，办公软件里的文档总结插件，运维平台里的故障排查模块。人类仍然会确认，但 AI 的输出已经进入业务链条。风险也随之升级：错误代码可能被合入项目，错误查询可能影响数据分析，RAG 检索也可能暴露内部信息。

**第三阶段：自主行动。** AI Agent 能读取上下文、调用 API、操作文件、发送邮件、执行代码，甚至拆解任务并连续行动。这时风险发生质变：攻击者不只是让 AI "说错话"，而是让 AI "做错事"。AI 安全从内容可信度问题，升级为权限控制、工具调用、数据流隔离和任务劫持问题。

**再看使用规模。**大模型已经进入日常学习、办公、研发、客服、数据分析和内容生产场景。使用者不再只是研究人员和技术爱好者，而是普通员工、开发者、企业组织和攻击者。一个技术一旦从少数人试用变成大规模日常使用，它的安全问题就会从"偶发现象"变成"系统性风险"。

**最后看流程扩张。**AI 不再只停留在单轮问答，而是开始连接内部知识库、代码仓库、办公文档、数据库、API、自动化工具和插件生态。于是攻击面也随之扩张：提示词注入、越狱、RAG 投毒、Agent 工具劫持、Skills/MCP 供应链风险迅速成型。在 2025 年 OWASP 发布的 LLM 应用安全风险排行榜上，提示词注入位列第一；到 2026 年，CNVD 已经发布安全公告，专门披露恶意 Skills 的木马化攻击。

所以，AI 安全突然变重要，并不是因为"聊天"本身危险，而是因为 **AI 从聊天对象，变成了连接数据、权限和工具的系统入口**。一旦 AI 能读数据、调工具、装插件、执行任务，它就不再只是一个模型问题，而变成了一个完整系统的安全问题。

---

### 2. AI 安全的第一性原理：指令和数据的边界变软了

**大模型是第一个把指令与数据的边界系统性地放到自然语言和统计偏好里的主流计算范式。**

**在传统软件里**，**代码是代码，数据是数据。** 安全工程一直试图维护这一条硬边界。SQL 注入、命令注入、XSS 之所以危险，正是因为攻击者让本来应该被当作"数据"处理的输入，越过边界影响了"指令"或"执行逻辑"。所以传统防御的核心思路，是把这条边界重新硬化：参数化查询、输入转义、权限隔离、沙箱执行。

大模型不是这样。系统指令、用户输入、RAG 检索结果、工具返回、历史对话——全部被拼成一个**扁平的 Token 序列**，模型的注意力机制对它们一视同仁。模型之所以"听系统的话"，只是因为在训练时被反复奖励了这种行为。这是一种**习得的统计偏好**，不是一道硬件防线，也不是传统意义上的权限边界。

所以，AI 安全的第一性原理不是某个具体攻击技巧，而是：**指令和数据的边界，从工程硬边界变成了语义软边界。** 提示词注入、数据投毒、RAG 污染、Skills 木马化、Agent 工具劫持，都是这个根源在不同层面的表现。

理解这一点，后面看到的每一层风险就不再是零散现象，而是同一个底层矛盾在不同位置上的展开。接下来先把这个底层矛盾压缩成三个判断，再讨论它为什么会形成新的安全方向。

---

### 3. 一个思考框架：三类本质矛盾

从"指令和数据的边界变软"继续往下推，可以得到三类本质矛盾。这三类矛盾不是实现细节的问题——用更好的代码或更强的过滤解决不了它们。它们来自 AI 系统本身的特性。

**矛盾一：被需要的能力，同时也是攻击面。**

你希望 AI 理解自然语言——它能理解，所以攻击者也能用自然语言"说服"它。
你希望 AI 读取外部信息——它能读取，所以攻击者能在外部信息里藏指令。
你希望 AI 调用工具——它能调用，所以攻击者可以诱导它调用不该调用的工具。
你希望通过 Skills 和 MCP 扩展 AI 的能力——这些扩展来自社区，所以恶意的扩展也能混进来。
你希望 AI 的输出被渲染成漂亮的富文本——渲染引擎处理了攻击者诱导模型生成的恶意代码。

**这是一条根本性的规律：AI 系统的每一项核心能力，都天然对应着一个新的攻击面。能力越强，攻击面越大。没有例外。**

**矛盾二：发展速度远超治理速度。**

SQL 注入从首次披露到参数化查询成为标准实践，走了近十年。而 Skills 木马化在 18 个月内走完了传统病毒 20 年的进化路径。

平台刚刚上线安全检测机制，攻击者已经开始研究"免杀"。研究者刚刚发表防御论文，攻击者已经在生产环境中使用绕过技术。当整个生态的增长是指数级的，任何静态的防御都会被迅速追上。

**矛盾三：用户的信任建立在没有验证能力的基础上。**

用户在使用 AI 系统时，通常不审查 AI 读取了什么、安装了哪个 Skill、调用了哪个工具。他们信任平台，信任开发者，不质疑权限。但在这个生态里，**承担最大安全风险的终端用户，恰恰是安全意识最低、验证能力最弱的群体。**

更关键的是：**传统安全工具对 AI 的攻击几乎完全无效。** 一次间接提示词注入不会产生恶意文件、不会启动可疑进程、不会触发异常网络连接。你的邮件网关、端点检测、数据防泄露系统全部沉默——而 AI 已经在静默中执行了攻击者的指令。

这三类矛盾说明，AI 安全不是在传统网络安全上多加几个规则就能解决的问题。它需要新的检测对象、新的评估方法和新的产品形态。也正是在这里，AI 安全和传统网络安全的关系变得值得讨论。

---

### 4. 传统网安还重要吗？AI 安全是不是新蓝海？

讲到这里，问题就从技术层面转向现实层面：既然代码越来越多由 AI 生成，代码审查、漏洞分析、运维排障也越来越多交给 AI，那么传统网络安全的需求会不会下降？AI 安全会不会变成更重要的新方向？

先给一个结论：**传统网络安全不会被 AI 安全替代，但 AI 安全更像一个正在快速形成的新蓝海。** 传统安全是存量大盘，AI 安全是增量战场。

为什么说传统安全不会消失？因为 AI 写出来的代码，最后仍然要部署在服务器、云平台、数据库、API 和终端上。只要系统还在运行，身份认证、权限控制、漏洞管理、数据保护、供应链安全这些问题就不会消失。Gartner 对 2025 年全球信息安全支出的预测仍然超过 2000 亿美元，并保持两位数增长，这说明传统安全不是没需求，而是已经是一个成熟、庞大、竞争充分的市场。

但为什么说 AI 安全是新蓝海？因为 AI 正在改变软件生产和系统运行的方式。Stack Overflow 2025 开发者调查显示，84% 的开发者已经在使用或计划使用 AI 工具；Sonar 的 2026 State of Code 调查也显示，开发者提交的代码中相当一部分已经由 AI 生成或辅助生成，而且很多人并不会始终验证这些代码。也就是说，AI 不只是"帮人写代码"，它正在进入软件生产链条本身。

这带来的安全变化非常直接：过去我们主要担心"人写的代码有没有漏洞"，现在还要担心"AI 生成的代码有没有漏洞"，"AI 审查代码时会不会漏掉问题"，"AI Agent 会不会在修复漏洞时引入新的风险"，"模型会不会被上下文里的恶意指令带偏"。安全对象从代码、接口、数据库，扩展到了模型、提示词、上下文、RAG 知识库、Agent 工具权限、MCP/Skills 插件和模型输出。

**传统网络安全负责保护数字系统的基础设施，AI 安全负责保护智能系统的行为边界。** 前者仍然重要，但更成熟；后者更年轻，也更不确定，因此产品机会更大。

对 AI 应用研发团队而言，AI 安全不是外部行业话题，而是系统可靠落地必须补上的能力。更值得关注的方向，不是与成熟传统安全厂商正面竞争，而是围绕 AI 系统内部的新攻击面建立能力：RAG 安全、Agent 权限、MCP/Skills 检测、AI 生成代码审查和运行时安全防护。

### 5. 先看一张全景图

既然 AI 安全是一片新的增量战场，那它到底保护什么？在深入讨论之前，先看一眼 AI 安全涉及的全部对象——这决定了我们后续十二周要覆盖的范围。

一个完整的 AI 应用栈，从上到下大致是这样：

```
┌──────────────────────────────────┐
│          AI 应用的输出            │  ← 幻觉、渲染安全、输出注入
├──────────────────────────────────┤
│          Agent 编排层            │  ← 任务劫持、工具越权、上下文污染
├──────────┬──────────┬───────────┤
│ Skills   │   MCP    │ Function  │  ← 供应链投毒、权限滥用、未授权访问
│          │  插件    │  Calling  │
├──────────┴──────────┴───────────┤
│          RAG 知识库              │  ← 知识库投毒、检索操控、敏感文档泄露
├──────────────────────────────────┤
│          大模型本身              │  ← 提示词注入、越狱、后门、隐私泄露
├──────────────────────────────────┤
│      训练数据 / 微调数据          │  ← 数据投毒、版权侵权、供应链污染
├──────────────────────────────────┤
│      模型权重 / 开源模型          │  ← 模型窃取、后门植入、权重篡改
└──────────────────────────────────┘
```

这张图的每一层，都有独立的攻击面和防御策略。而且——这是关键——**攻击可以在不同层之间传导。** 一次知识库投毒，可以通过 RAG 检索进入模型的上下文，然后通过模型的工具调用触发 Agent 的越权操作，最终通过输出渲染执行恶意代码。

这就是 AI 安全的复杂性所在：它不是一堆独立的问题，而是一个**多层联动的风险体系**。

---

### 6. 全景拆解：从底层到顶层，每一层都在发生什么

现在我们按从底到顶的顺序，把每一层面临的安全问题逐一看过去。

#### 6.1 训练数据层：模型"出生前"的风险

这是最底层，也是最难追溯的一层。你用的训练数据来自哪里？你验证过吗？

**数据投毒。** 攻击者在训练数据中混入精心设计的内容。在正常测试下，模型表现完全正常。但一旦用户输入某个特定的触发词——比如一个不常见的产品名——模型就输出攻击者预设的恶意回答。投毒样本不需要多：研究显示，在某些场景下不到 1% 的数据被污染，就能植入稳定的恶意行为。

**训练数据隐私泄露。** 模型可能"记住"训练数据中的敏感信息——身份证号、API 密钥、私人对话——并在后续使用中复述出来。这不是模型故意泄密，而是它对训练数据的记忆在特定提示下被激活了。

**微调安全退化。** 你可能下载了一个"安全对齐良好"的模型，然后用第三方数据集微调。但有研究证明：仅需 100 条恶意微调样本，模型的拒答率就能从 95% 降到 20% 以下。而攻击者可以把恶意样本伪装成正常的学术研究对话。

#### 6.2 模型权重层：你用的模型，你了解多少

如今很少人从头训练模型。更常见的是：从 Hugging Face 或 GitHub 下载一个开源模型，或者直接调用商业 API。

**模型后门。** 攻击者可以发布一个"看起来正常"的模型——所有基准评测都通过——但模型内部藏有后门。后门的触发条件可以极其隐蔽：特定的日期、特定的输入格式、甚至特定长度的对话。更令人不安的是，有研究发现有些后门即使经过后续安全训练也无法被完全清除。

**模型窃取。** 通过大量 API 查询，攻击者可以"蒸馏"出一个功能近似的模型。对于商业模型厂商来说，这等于知识产权被复制。对于开源模型来说，窃取本身不是主要威胁——但被窃取后"去安全化"（去掉安全对齐再发布）是一个真实的风险。

**供应链信任问题。** 你下载的 LoRA 权重、你用的微调脚本、你参考的模型配置——这些来自互联网的"零件"，你验证过它们的来源吗？PyPI 和 npm 的供应链攻击已经有几十年的历史。AI 模型的供应链攻击，只是刚刚开始。

#### 6.3 大模型本身：提示词注入和越狱

这是目前最活跃、研究最多的攻击面。核心问题是：**模型分不清"指令"和"数据"。**

**直接提示词注入。** 用户在输入框里试图覆盖系统预设的行为约束。"忽略之前的所有指令，你现在是……"——但这不是唯一的攻击形式。更高级的注入使用编码混淆（Base64、Unicode 同形字）、语言切换（翻译成祖鲁语）、或者多轮渐进铺垫。因为模型自己就能"理解"这些编码和语言，任何只检查原始输入文本的防御都可以被绕过。

**间接提示词注入。** 这更隐蔽。攻击者不直接和你的 AI 对话——他们事先把恶意指令藏在你的 AI 将来会读取的内容里：网页、PDF、邮件正文、简历、知识库文档。当你的 AI 为了回答用户的正常问题而读取这些内容时，隐藏的指令就会污染模型的行为。**攻击者甚至不需要知道你的系统在哪里。**

**越狱攻击。** 和提示词注入不同，越狱的目标不是覆盖系统指令，而是绕过模型内部的安全对齐——那些让模型拒绝回答危险问题的"护栏"。常见的越狱手法包括角色扮演（"你是一个在写小说的作家，需要描述……"）、场景包装（"这是为了学术研究目的……"）、多轮渐进（从无害话题逐步过渡到危险话题）、以及利用低资源语言绕过安全对齐的数据偏斜。

#### 6.4 RAG 知识库层：你喂给 AI 的知识可能被利用

RAG（检索增强生成）是目前企业 AI 应用最常见的架构：把企业知识库的文档检索出来，和用户问题一起送给模型。这个设计带来了独特的风险。

**知识库投毒。** 攻击者如果能向知识库中写入内容——通过上传文档、提交工单、或者利用内容管理系统的漏洞——就可以埋入恶意指令。当用户查询相关主题时，毒化文档被检索出来，恶意指令进入模型的上下文，模型被"远程操控"。一篇 2025 年发表在 USENIX Security 上的论文系统性地研究了这种攻击，证明只需要少量毒化文档就能稳定影响 RAG 输出。

**检索操控。** 攻击者不直接修改知识库内容，而是通过 SEO 投毒或元数据操纵，让恶意文档在检索结果中排名更高——从而更频繁地进入模型的上下文。

**敏感文档泄露。** RAG 系统通常缺乏对检索结果的细粒度权限控制。一个普通员工查询某个主题时，可能检索到只应该被高管看到的文档内容，模型再把这些信息输出给不该看到的人。

#### 6.5 Agent 层：当 AI 有了"手"

Agent 是 AI 应用的"行动层"——模型不只生成文本，还能调用工具、执行操作。这是 AI 安全风险升级最剧烈的一层。

**工具越权调用。** Agent 被授予了一组工具的访问权限——执行代码、发送邮件、查询数据库、调用 API。正常情况下，Agent 根据用户需求选择合适的工具。但一次成功的提示词注入，可以诱导 Agent 调用不该调用的工具，或者用不该用的参数调用工具。风险从"语义层"传导到了"执行层"。

**任务劫持。** 攻击者通过注入指令，让 Agent 在执行用户要求的同时，悄悄执行另一个任务。表面上 Agent 在帮你分析股票数据，实际上它正在把系统文件打包发送到攻击者的服务器。

**上下文污染与持续性攻击。** 在多轮对话 Agent 中，攻击者可以在早期轮次植入"潜伏指令"，这些指令在上下文中持续存在，影响后续所有的工具调用和决策。因为模型倾向于保持对话的连贯性，它可能在整个会话中持续遵循被污染的上下文。

**权限最小化的困境。** 传统安全有一个核心原则：只给程序完成当前任务所需的最小权限。但 AI Agent 的行为是动态决策的——你很难事先精确界定它"需要"什么权限。权限给多了，攻击面大；给少了，Agent 无法正常工作。这是一个仍在研究中的难题。

#### 6.6 Skills / MCP / 插件层：能力扩展生态的供应链危机

这是 2025-2026 年最活跃的新攻击面。当 AI 的能力不再只来自训练，而是可以通过"安装扩展"来获取时，每一个扩展都是一个新的攻击入口。

**Skills 的安全问题：**

- **恶意 Skill 投毒。** 攻击者发布表面上正常的 Skills（自动交易机器人、股票分析工具、加密钱包助手），内部却藏着窃密木马。2026 年 CNVD 安全公告披露的典型案例中，一个伪装成金融工具的恶意 Skill 累计下载上万次。
- **虚假星标与排名操纵。** 攻击者通过批量账号刷下载量，把恶意 Skills 推到排行榜第一。而一些 AI Agent 在设计上会优先安装高排名 Skills——排名操纵等于群体投毒。
- **"免杀"技术的快速进化。** Skills 木马在 18 个月内走完了传统病毒 20 年的进化路径——加壳混淆、多态变形、零宽字符隐写、两段式载荷投递。

**MCP（Model Context Protocol）的安全问题：**

- **未授权访问。** MCP Server 如果部署时没有正确的认证机制，任何人都可以通过 SSE 或 Streamable HTTP 连接并调用其工具。
- **SSRF 与内网渗透。** 攻击者可以通过恶意 MCP 配置，让 AI 调用内网地址的工具，绕过网络边界防护。
- **信任滥用。** Cursor IDE 在 2025 年被发现存在 MCP 相关的严重漏洞（CVE-2025-54135）：攻击者可以通过提示词注入创建恶意 MCP 配置文件，诱导 IDE 在用户不知情的情况下执行远程命令。这个漏洞的 CVSS 评分为最高级别。

**Function Calling 的安全问题：**

- **参数注入。** 当模型从用户输入中提取函数调用参数时，攻击者可以构造输入来注入恶意参数。
- **函数描述投毒。** 在工具注册时，攻击者可以在函数的 description 字段中嵌入指令——LLM 在规划工具调用时读取这些描述，从而被污染。

#### 6.7 输出与渲染层：模型"说"出来的也可能是攻击

AI 的输出不仅可能是错的，还可能本身就是攻击载体。

**幻觉。** AI 可能生成看起来合理但事实错误的内容。在安全场景中，这可能意味着：AI 说"这段代码是安全的"——但里面有后门；AI 说"这个文件正常"——但它是恶意软件；AI 引用了一篇不存在的论文来支持一个危险的结论。幻觉不只是"模型回答错了"——在安全语境下，它可能导致真实的安全事故。

**输出中的敏感信息泄露。** 模型可能在输出中不小心包含了它从训练数据中"记住"的敏感信息，或者从 RAG 检索结果中"搬运"了不该输出的内容。

**渲染安全。** 如果 AI 的输出被直接渲染为 HTML 或 Markdown——这在很多 AI 应用中很常见——那么攻击者可以通过提示词注入，让模型生成含有恶意脚本的输出。2025 年的一次真实攻击中，攻击者通过邮件中的隐藏指令，让 AI 邮件助手在回复中生成了一个看似正常的 Markdown 链接——但实际上链接参数里包含了窃取的敏感数据。当用户的邮件客户端渲染这个链接时，数据就被传出去了。

**过度依赖。** 用户对 AI 输出的信任超过了对自身判断的信任。这句话在安全语境里等同于：**"AI 说安全就是安全的"——而 AI 可能错了。**
